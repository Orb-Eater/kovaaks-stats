## 0. Blockers — fix before trusting T1, T4, T5

### 0.1 Sensitivity fields did not parse **[BLOCKED]**

`configs  s?/d?/? = 21775` — every run reported unknown sens, DPI and scale.

Consequences:

- **T9 (cm pooling) could not run at all.** The spec's claim that pooling sensitivities
  inflates variance remains untested on this corpus.
- **T1, T4 and T5 pooled all sensitivities.** This user plays ~35–40 cm/360 in one game
  and ~63 cm in another. Runs at different sensitivities landing in different sessions
  means **between-session sensitivity variation is currently being counted as
  between-session score variation**, which inflates ICC.

**Action:** correct the field names in the parser, rerun, and treat T1's ICC as an upper
bound until then.

### 0.2 Scenario count is implausible **[BLOCKED]**

2,119 scenarios across 21,775 runs is 10.3 runs each. Possible for a large playlist
library, but also the signature of a name parser that fails to strip a suffix and splits
one scenario into several near-duplicates.

**Action:** sort the scenario list by name and look for adjacent near-identical entries.
If they exist, every per-scenario statistic is fragmented and the reachability numbers in
§5 are pessimistic.

### 0.3 Restart contamination is real, and large **[CONFIRMED]**

26.46% of runs have no usable elapsed time or kill rows. Independently corroborated: a
session screenshot showed 12 restarts in 41 runs (29%).

**Roughly a quarter of logged runs are abandoned attempts.** Verify the `is_reset`
exclusion is actually firing in the live build. If it is not, every historical number
includes them, and abandoned attempts are systematically low.

## 1. Warm-up is time-indexed, not run-indexed **[REVISED]**

> **V3 and V3.1 both indexed warm-up on run count.** Wrong axis.

```
minute curve   89.9  100.8  102.0  103.3  99.8  98.8  99.7  97.7  101.8
run curve      95.5   94.9   97.7   98.7  101.0 102.3  93.3 101.7 103.8 105.3 105.1 100.2

tau_minutes    0.37          tau_runs   1.82
peak                          peak_at_run 22 (107.9%)
warmup_z       3.71  -> distinguishable YES
warmup_magnitude 4.51%
```

The minute curve behaves like a warm-up curve: depressed through the first bucket, then
flat. The run curve never saturates — it climbs past 105% by run 10 and peaks at run 22,
which is not what an exponential approach to plateau looks like.

Corroboration from an independent test: **T10 cold-start runs sit at 91.25%**, essentially
the same figure as the first minute bucket at 89.9%.

### 1.1 Two honest caveats on this finding

- The SSE comparison (`runs 30.34` vs `minutes 2.65`) **overstates the gap**. The minute
  curve has 9 buckets against the run curve's 30, and fewer buckets are mechanically
  smoother. Do not quote the 11x.
- The run-indexed curve has a **composition artifact**: index 22 draws only from sessions
  that reached 22 runs on one scenario, while index 1 draws from all of them. Different
  positions come from different populations. This is likely *why* `tau_runs = 1.82`
  contradicts `peak_at_run = 22`, and it argues for distrusting the run curve rather than
  for trusting the minute curve.

The conclusion still holds — the time-indexed curve is the one with a clean plateau — but
it rests on curve shape and the T10 agreement, not on the SSE ratio.

### 1.2 What to build

```
WARMUP_MODE      = 'elapsed'          // was 'runs'
WARMUP_SECONDS   = 120                // fitted; recalibrate per install
// exclude runs whose start is < WARMUP_SECONDS after session start
```

`WARMUP_DROP: 2` was not wrong by accident: at this user's 67-second median inter-run gap,
2 runs is about 2¼ minutes, which lands close to the fitted 120s. **That is coincidence,
not design**, and it breaks the moment pacing changes — a session with 20-second gaps
would have 2 runs covering 40s and stay contaminated.

The V3.1 §A.1 evidence gate still applies and **passes here** (z = 3.71). The correction
is warranted for this user. Keep the gate for users where it is not.

### 1.3 The profile readout is worth shipping

`warm after ~2 minutes; the first 2 minutes cost you about 10%` is directly useful advice
and falls out of the fit for free. V3.1 §A.3 stands, with `better_predictor` now known to
be `minutes` for this corpus.

## 4. Noise and reachability **[CONFIRMED]**

```
cv_run_median       8.98%   (p25/p75  6.9 / 12.3)
cv_session_median   6.97%
swc_pct             2.69%
sessions_per_side   105
```

Note that `cv_session` is only slightly below `cv_run`. That is the expected consequence of
ICC 0.58: session means do not average down much when observations inside a session are
strongly correlated. T1 and T4 are internally consistent.

At ~20 sessions/month (448 sessions over 22 months), 105 sessions per side is **5 months
per side, 10 months per comparison**, for a single scenario.

### 4.1 T12: zero of 70 scenarios currently measurable

`SmoothBot_Perfected` is closest at 10 sessions against 10 required. Nothing clears the
2x margin.

This is the product decision V3 §18 anticipated, now with a number. **Recommended
resolution:**

1. **Benchmark aggregate becomes the headline** (V3 §10a). The external rank threshold is
   the only effect size in the app that does not scale with the user's own CV, and
   therefore the only one with a reachable sample size.
2. **Scenario-level numbers render as `within noise`** with their session count and the
   count required. Per V3 §6 this is already the correct rendering; T12 means it is the
   rendering for essentially everything.
3. **Offer a "tracked scenarios" list of 2–3** that the user commits to, with the app
   reporting progress toward measurability rather than a fabricated percentage.

## 5. Familiarisation: lambda is 13x the spec's assumption **[REVISED]**

```
exp_wins 41   pow_wins 4        lambda_median 66.69 runs
near_asymptote_at 200 runs
```

Heathcote reproduces decisively — exponential over power law, 41 to 4. V3 §9's functional
form is right.

**The constant is not.** `REFAM_DROP: 5` assumed familiarisation resolves in a handful of
runs. It takes ~67 runs to decay by 1/e and ~200 to approach asymptote.

Consequences:

- `REFAM_DROP` should be derived from fitted lambda, not fixed at 5. Given the magnitude,
  post-gap exclusion may be better replaced by **curve correction** — subtracting the
  fitted familiarisation term rather than discarding 67 runs.
- With 2,119 scenarios and only 77 above 60 runs, **the overwhelming majority of the
  library has never reached asymptote**. Most scenario-level movement in the app is
  familiarisation, not aim.
- The V3 §9 rule "mark a cell in familiarisation while `k < 3*lambda`" now excludes
  almost everything at `3 * 67 = 200 runs`. That is the correct behaviour and it should
  not be softened to make the UI look busier.

## 6. Fatigue is not optional **[REVISED]**

```
session length   5-10   11-20   21-35   36-60   61+
value (% scen)   99.2   101.8   100.7   106.7   94.0
spearman_r       0.1057
```

An inverted U, not a slope. Performance rises to the 36–60 run band, then collapses 12.7
points at 61+.

V3 §5.4 treats the fatigue term `- f * max(0, i - i_fatigue)` as part of the model but
`FATIGUE_MIN_RUNS: 15` gates it off for shorter sessions. **The fatigue term is
load-bearing and must be fitted wherever session length permits.** A warm-up-only model
fits this curve badly.

This also explains the 2026-09-02 dip completely: sub-15 and sub-30 sessions sit at 101.8
and 100.7 against 106.7 for the 36–60 band. **A shift toward short sessions costs 5–6%**,
which is five times the +1.0% that was being read as signal.

## 9. What this run did not settle

- **cm/360 as a confound.** Untested; parser failure. This is the largest open question,
  because it bears directly on whether ICC 0.58 is real.
- **Whether `warmup_seconds` is stable across scenario types.** A single global constant
  is assumed; tracking and clicking scenarios may differ.
- **Benchmark aggregate CV.** Not measured — the tool has no benchmark identification.
  The `CV_agg = CV * sqrt((1+(k-1)r)/k)` claim in V3 §10a remains theoretical, and the
  case for making benchmarks the headline rests on the external-threshold argument alone
  until it is measured.
