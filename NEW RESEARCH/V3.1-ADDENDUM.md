## A. Corrections do not apply unconditionally **[corrects V3 §4b, §5.4]**

> **V3 said:** fit `tau` per install, use `ceil(tau)` as the drop count.
> That is still right *when warm-up exists*. V3 never said what to do when it doesn't.

Dropping runs costs sample size. On a 15-run session, dropping 2 discards 13% of the
data. If the warm-up effect is not distinguishable from zero for a given user, that
trade is strictly negative: **you lose power to correct a bias you do not have.**

### A.1 Gate every correction on evidence

```
warmup_magnitude = plateau - first_run_mean
warmup_se        = sqrt( se(first_bucket)^2 + se(plateau_buckets)^2 )
warmup_z         = warmup_magnitude / warmup_se

if |warmup_z| < 1.96:
    WARMUP_DROP = 0                 // use every run; correcting would cost accuracy
    flag: "no measurable warm-up effect for this user"
else:
    apply the §5.4 fit
```

The same gate applies to `REFAM_DROP`. Measure the re-familiarisation effect, and if it
does not clear zero, do not exclude anything.

### A.2 Prefer modelling over trimming

This is the deeper form of the same point and it was already implicit in V3 §3, but not
stated as a principle.

Trimming throws runs away. The fitted plateau `P` uses **every run in the session**,
including the warm-up ones, and corrects for position rather than discarding. It is
strictly more efficient than a trimmed mean at the same correction quality.

**Ranking, best to worst:**

1. Fitted plateau `P` — uses all runs, corrects for position. Default when the session
   has enough runs to fit.
2. Trimmed mean of post-warm-up runs — discards data. Fallback below `FIT_MIN_RUNS`.
3. Raw session mean — correct when A.1 says there is no effect to correct.

Never trim when you can fit.

### A.3 Warm-up profile as a user-facing readout **[NEW]**

Once `tau` is fitted, the app already knows something the user wants: **how long their
warm-up actually takes and where performance peaks.** Surface it.

```
warmup_profile = {
  tau_runs,               // fitted constant, run-indexed
  tau_minutes,            // same fit, elapsed-time-indexed
  better_predictor,       // whichever has lower SSE per point
  peak_position,          // argmax of the fitted curve
  peak_magnitude,         // plateau as % of first-run mean
  distinguishable         // the A.1 gate
}
```

**Fit both indexings.** Warm-up may be driven by elapsed time (physiological) or by run
count (task-specific re-entry), and these differ for a player who takes long breaks
between runs. Whichever fits better is the one the correction should be indexed on, and
that is an empirical question per user, not a design choice.

Test `T2b` in the validation tool computes all of this.

## B. Harrell-Davis — right change, wrong reason **[corrects V3 §5a, SPEC-REVISIONS Fault 1]**

> **V3 said:** the traditional p90 rises when a new PB is added because the percentile
> index shifts, and Harrell-Davis fixes this by weighting all order statistics.
>
> **The first half is right. The second half is false.** Simulation on normal samples,
> n = 15–40, 400+ replications:

| Perturbation | Traditional p90 | Harrell-Davis |
|---|---|---|
| one new max added | 1.12 units | 1.63 units |
| one ordinary run added | 0.135 | 0.183 |

**HD moves *more*, not less** — about 1.3x more — because the maximum carries positive
beta weight at p=0.90, so a new high value pulls the estimate directly. The traditional
estimator only moves via the index shift.

The index-shift pathology is real, though. Traditional p90 moves 1.393 → 1.569 as the new
PB goes from +0.1 to +3.0 above the old best: **a PB thirty times better moves the ceiling
only 13% more.** It responds to the *fact* of a new max, nearly ignoring its size. HD at
least responds proportionally (1.570 → 1.952).

### B.1 The actual reason to switch: n-dependent bias

| n | Traditional bias | HD bias | HD variance ratio |
|---|---|---|---|
| 15 | **−1.368** | +0.235 | 1.049 |
| 25 | **−0.855** | +0.384 | 0.943 |
| 40 | **−0.503** | +0.280 | 0.893 |

(units are score units on a σ = 8 distribution; truth = 110.25)

The traditional p90 **systematically underestimates, and the bias shrinks as n grows.**
That is the defect that matters here, because the app compares two periods that rarely
have equal session counts:

> A window with 15 sessions against a baseline with 40 produces a spurious **+0.87%**
> ceiling change from bias alone, with no change in skill.

That is the same magnitude as the observed 2026-09-02 event, and a better explanation
than the index-shift story V3 gave. HD's bias is smaller and roughly flat in n, which is
the property the app needs.

### B.2 What to actually build

1. **Switch to Harrell-Davis** — for the bias, not the PB sensitivity. Keep the §5a
   implementation; only the rationale changes.
2. **Add n-matching, which V3 missed entirely.** Neither estimator is stable to a single
   run at these sample sizes, so the estimator alone does not solve this:

```
if (n_window / n_baseline > N_MATCH_RATIO ||
    n_baseline / n_window > N_MATCH_RATIO) {     // N_MATCH_RATIO = 1.5
  // subsample the larger side to the smaller side's n, average over
  // N_MATCH_REPS (25) draws, and widen the SE accordingly
}
```

Without this, every ceiling comparison across unequal periods carries a bias term the
estimator cannot remove.

3. **Do not claim HD fixes PB sensitivity.** It does not. Remove that sentence from
   §5a and from SPEC-REVISIONS Fault 1.

## C. Attribution — the retrospective scan **[extends V3 §10c]**

The forward version ("did playing X help Y?") is specified in V3 §10c. The retrospective
version — *scan everything and tell me what improved after I started playing X* — is the
same machinery with the search direction reversed, and it is far more dangerous.

Forward: one hypothesis, one test. Retrospective: every scenario tested against every
other, so with 187 scenarios the search space is tens of thousands of pairs, and the
largest apparent effect is almost certainly noise. This is the classic garden of forking
paths.

**It is still worth building, under these constraints:**

```
scan_result = {
  target,                    // the scenario or benchmark whose change is being explained
  candidate,                 // what might have caused it
  effect,                    // lagged, dose-response, per §10c
  null_percentile,           // position in the negative-control distribution
  n_comparisons,             // size of the search space actually scanned
  bh_threshold               // Benjamini-Hochberg critical value at that count
}
```

- **The negative-control distribution from §10c becomes mandatory here, not advisory.**
  With a large search space it is the only thing standing between the user and a
  confident false positive.
- **Report `n_comparisons` in the UI.** The user must see that 40,000 pairs were
  examined before reading the top one.
- **Rank, never threshold.** Present an ordered list with null percentiles. Do not
  render "significant" for anything.
- **Require a minimum effect.** Below the SWC from §7a, do not list a candidate at all,
  however extreme its percentile — an unmeasurable effect with a good p-value is still
  unmeasurable.
- **Frame as a starting point.** Output copy should be *"these are worth testing"*, not
  *"these worked"*. The alternating-block protocol remains the only thing that answers
  the question.

## E. What the validation tool decides

None of A or B depends on the corpus, but the corpus decides how much they matter:

| Test | If it says | Then |
|---|---|---|
| `T2b` distinguishable = NO | you have no warm-up effect | A.1 fires; set drop to 0 and skip gap #7 entirely |
| `T2b` better_predictor | minutes or runs | index the correction on that |
| `T5` n_driven_swing large | ceiling bias is real | B.2 n-matching is required, not optional |
| `T5` hd swing ≥ trad swing | HD does not help *here* | keep traditional, rely on n-matching alone |
| `T1` ICC ≈ 0 | runs are independent | the whole session rewrite (gap #8) is unnecessary |

Run it before building any of this. Two of the five rows above would remove work rather
than add it.
